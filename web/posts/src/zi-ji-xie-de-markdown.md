## 为什么要自己写

先说结论：这不是一个聪明的决定。

用一个成熟的 Markdown 库，两行代码就能搞定，还比我写得好。但我给这个博客定的规矩是：**整个站点是几个 HTML 文件加一小撮 JS，没有任何依赖、没有任何构建步骤。**

规矩一旦立了，就没得商量。所以解析器得自己写。

## 它需要支持什么

需求清单其实很短：

1. 标题（`#` 到 `######`，以及下划线式的 setext）
2. 围栏代码块与行内代码
3. 引用、分割线
4. 有序/无序列表，**要能嵌套**
5. 表格
6. 行内样式：粗体、斜体、删除线、链接、图片

剩下的交给浏览器——毕竟最后输出的就是 HTML。

## 核心思路

分两层：块级负责结构，行内负责修饰。块级逐行扫描，遇到"围墙"就把区间吃掉，剩下的按段落处理。

```js
/**
 * 块级解析：逐行扫描，遇到能开头的语法就吃掉对应区间
 * @param {string} md 原始 markdown（不含 front matter）
 * @returns {{html: string, headings: Array}} 正文 HTML 与目录数据
 */
function parseBlocks(md) {
  const lines = md.replace(/\r\n?/g, '\n').split('\n');
  const out = [];
  let i = 0;

  while (i < lines.length) {
    const line = lines[i];

    // ① 围栏代码块：找到收尾围栏，中间原样保留（只做转义）
    const fence = line.match(/^\s*(```+|~~~+)\s*([\w+#-]*)/);
    if (fence) {
      const code = [];
      const mark = fence[1][0].repeat(fence[1].length);
      i++;
      while (i < lines.length && !lines[i].trim().startsWith(mark)) {
        code.push(lines[i++]);
      }
      i++; // 跳过收尾围栏
      out.push(`<pre><code class="lang-${fence[2]}">${esc(code.join('\n'))}</code></pre>`);
      continue;
    }

    // ② 其余块级语法进入分发……
    i++;
  }
  return out.join('\n');
}
```

行内那层有个关键顺序问题：**必须先抽出代码段**，否则 `` `a*b*c` `` 里的星号会被当成斜体。

```js
// 先占位保护行内代码，解析完再还原
text = esc(text).replace(/`([^`]+)`/g, (_, code) => {
  codes.push(`<code>${code}</code>`);
  return `\u0000${codes.length - 1}\u0000`; // 占位符，几乎不可能与正文冲突
});
```

## 踩到的两个坑

**坑一：字符转义和语法解析的顺序。**

如果先解析语法再转义，用户写的 `<script>` 就能活下来；如果先转义再解析链接，`[a](b&c)` 里的 `&` 会变成 `&amp;`，链接就断了。最终方案是：整体转义 → 语法解析 → 只对 URL 做一次反向修正。

**坑二：嵌套列表。**

用正则递归是死路。最后用的是缩进栈：记录每一层列表的缩进值和标签类型，遇上更深的缩进就压栈开新列表，遇上更浅的就弹出。

> 写到这里我意识到，这个解析器的价值不在于它多好，而在于它有多可替换——如果哪天我想换掉它，只需要保证 `parse(md)` 返回同样的东西。

## 代价

代价是它一定会在某个奇怪的地方出错。比如三个星号连写、比如列表里嵌表格、比如 HTML 实体。

但我接受这个代价。因为这个站点从今天起，只要浏览器能打开 HTML，它就能跑。**不引依赖、不走构建，换来的是一种很朴素的安全感：这里没有会过期的版本号。**
